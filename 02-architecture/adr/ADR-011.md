## Context

Penggunaan klien Supabase perlu konsisten (SSR/Browser) dan aman (tanpa hardcode URL/key di klien).

## Decision

Gunakan factories untuk SSR/Browser, audit bundling dengan `ci:guard`, dan standarkan impor di apps/packages. Implementasi menyertakan adapter server khusus untuk `apps/web` yang menggunakan `@sba/supabase/clients/node-admin` (Service Role) untuk rute API server-side, serta alias shim untuk pengujian agar tidak mengakses kunci rahasia di lingkungan test.

## Alternatives

- Hardcode config di klien: berisiko kebocoran.
- Satu klien untuk semua: tidak cocok untuk SSR.

## Consequences

- Pro: keamanan lebih baik, konsistensi integrasi; tidak ada hardcode URL/key di klien.
- Kontra: disiplin impor dan guard diperlukan; perlu shim test untuk adapter server di `apps/web`.

## Implementation Notes

- `apps/web/src/lib/supabase/server.ts` membuat klien server menggunakan Service Role (`createAdminClient`). Digunakan oleh rute API: `meta-events`, `meta-events/aggregates`, `audit/*`, dan `notifications/*`.
- Pengujian memakai alias Vitest: `@/lib/supabase/server` → `src/test/shims/supabase-server.ts` untuk mencegah akses kredensial saat test.
- RBAC test-mode dibatasi hanya untuk resource `analytics` agar tidak mempengaruhi resource lain (tenants, runs) saat pengujian.
